# ADR-008: 投稿の編集（内容の全置き換え・写真の足し引き・プレビューの取り直し）で確定した決定

- ステータス: 承認
- 日付: 2026-09-04

## コンテキスト

requirements.md 機能要件 11「投稿の編集 — 記録した内容をあとから直せる（打ち間違い・あとから足す写真・貼り替える URL）」を実装する（2026-09-03 のユーザ指示で Phase 3 を再開しての最優先）。

ADR-003 §5 は「編集 API は持たない（MVP。修正は削除 → 再投稿）」と決め、ADR-005 のサジェストはその線で「前回を複製して新規投稿」を実装した。**この判断を本 ADR で覆す**: 削除 → 再投稿は打ち間違い 1 文字のために写真（原本がスマホから消えていれば戻せない）・またたべたい・記録した日時・リンクプレビューを捨てる。思い出を捨てさせる作りは製品意図 1「振り返って思い出を楽しむ」に反する。

migration は無い（列も表も増えない）。決めるのは API の形・タグとプレビューの直し方・誰が直せるか・UI の置き場。

## 決定

### 1. 編集は「内容の全置き換え」= `PUT /meals/:mealId`（部分更新にしない）

body は作成と同じスキーマ（`CreateMealInput` を `MealContentInput` に改名して共用）で、`name` / `eatenOn` / `mealType` / `recipeUrl` / `shopUrl` / `recipeMemo` / `note` / `tags` の全部を毎回送る。PATCH の部分更新は「キーが無い＝据え置き」と「null＝消す」という **2 種類の不在**を body に持ち込み、型で区別できない曖昧さを増やす。フォームの state（`MealFormState`）は元から全項目を持つので、置き換えなら作成と編集で入力の意味が 1 つになり、zod スキーマも入力欄も 1 セットで足りる。

`mataTabetai` は body に入れない — 直すのは記録の内容で、♥ は家族の反応。トグルは `PATCH /meals/:mealId { mataTabetai }` のまま（欄が重ならないので競合しない）。写真も入れない（§4）。応答は一覧と同じ `MealSummary`（`listMeals` の結合を 1 件版 `getMeal` に切り出して使う）。

### 2. 認可はスペース、`created_by` は見ない

メンバーなら誰でも直せる（削除・またたべたい と同じ線）。認可軸は `space_id` だけで `created_by` は表示・監査用（ADR-003 §3、CLAUDE.md）— 編集にだけ持ち込むと「消せるのに直せない」ねじれが残る。実際にも親が子の打ち間違いを直す。`created_by` / `created_at` は編集で動かさず（記録したのが誰かは事実）、動くのは `updated_at` だけ。「誰が直したか」の列は持たない（家族数人で問う場面が無い。要るとなったら additive に足せる）。同時編集は last write wins。

### 3. タグは meal_tags を張り替える（差分を取らない）

タグ名の upsert（`ON CONFLICT DO NOTHING`）→ `DELETE FROM meal_tags WHERE meal_id = ?` → `INSERT … SELECT` を、作成と同じ 1 つの `d1.batch` に入れる。`meal_tags` は結合行だけで固有の情報を持たないので、差分計算は同じ結果に手間を足すだけ。使われなくなった `tags` 行は残す（サジェストの語彙。ADR-003 §4）。

凍結列は UPDATE でも毎回 `frozenRecipeColumns(recipeMemo)` から導出して書く。作り方メモを消す編集で `recipe_source_type` を `'text'` のまま残すと CHECK 違反で書き込みが落ちる — ADR-007 §2 の凍結は**書き込みごとの義務**であって作成時だけの話ではない。

### 4. 写真は既存の子リソース API のまま（編集の body に入れない）

`POST /meals/:mealId/photos` と `DELETE …/photos/:photoId` は既にあり、UI が無いだけだった（ADR-004 §6「投稿後の写真追加 UI は要望が出たら足す」の受け取り）。編集フォームの写真欄は保存ボタンを待たずその場で足し引きする — meal は既にあるので、作成時のような「送信まで手元に貯める」概念が要らない。取り消しは「戻す」ではなく「もう一度足す」。

### 5. URL を貼り替えたらプレビューを取り直す（同じ URL なら触らない）

kind ごとに、保存済みの `meal_link_previews.url` と新しい URL を比べる:

- 同じ → 行はそのまま（カードは投稿時点の姿のまま。ADR-007 §3）
- 変わった / 消した → 旧行を消し、R2 の画像も消す（R2 が先 — ADR-004 §6）。新しい URL があれば `pending` 行を立て直し、応答後の `waitUntil` で取りに行く（作成と同じ経路）

プレビュー画像の配信 URL は `/link-previews/:kind/image` で kind ごとに固定なので、貼り替えても URL は変わらない。写真（id ごとに不変）と違って**同じ URL の中身が変わる**ので、この route だけ `Cache-Control: private, no-cache`（ETag で毎回検証 = ふだんは 304）にする — `max-age=3600` のままだと、貼り替えたのに 1 時間前のサイトの画像が出る。

「同じ URL の取り直しボタン」は持たない。カードが古いのは思い出用途ではむしろ正で、直したいときは URL を貼り直せばよい。ADR-007 §5 の「再取得の導線は持たない（投稿の編集 API が無い）」はこの形で更新される。

### 6. プレビューの書き込みを「自分が取りに行った URL」に限る

投稿の数秒後に URL を直すと、前の URL の `waitUntil` が後から `ok` を書き、**新しい URL の行に古いサイトのカード**が乗る。塞ぎは 2 つ:

- ジョブの UPDATE に `AND url = ?` を足す（自分が取りに行った URL の行でなければ 0 行 = 何も書かない）
- og:image の R2 キーを取得ごとに固有にする: `ogp/<spaceId>/<mealId>/<kind>/<uuid>`。いまのキーは kind までで、2 つのジョブが同じキーに put し合うと**負けた側の補償削除が勝った側の画像を消す**。キーは行の `image_r2_key` が持ち、配信も削除も行から読むので末尾を足しても他は変わらない（migration も backfill も無い）

負けたジョブは自分が置いた object だけを消して終わる（meal が消えたときの既存の分岐と同じ）。

### 7. UI は一覧の行をその場で編集フォームに変える

「編集」を押すとその行が入力欄に変わる。`MealList` は みんなの記録 と ふりかえり の共通コンポーネント（ADR-006 §4）なので、どちらの一覧でも直せる。スマホで一覧の位置を失わず、戻る操作もスクロール復元も要らない（専用ページなら要る）。欄は投稿フォームと同じ部品（`MealFields`）を共有し、サジェストの札は出さない — 引き継ぎは「新しく記録する」ための道具で、編集の場に置くと自分の記録を他の回で上書きできてしまう。保存後は行をサーバー応答で置き換え、日付を変えたときは日付見出しごと並べ直す（一覧の並びは `eaten_on DESC, created_at DESC`）。料理名・タグが変わればサジェストも変わるので、既存の `onRecordsChanged` で再読込する。

### 8. テストの分担

- unit: `Meal → MealFormState` の逆変換（`mealFormFrom`）と、プレビューの差分判定 `previewPlan`（kind ごとに keep / replace / drop）を純粋関数に切って固定する。型では表せない意味なのでユニットの担当
- e2e: golden path に「記録 → 編集で料理名・タグ・食べた日を直す → リロードしても残る」を 1 本足す。URL 貼り替えの取り直しは link-preview spec の固定 HTML（ADR-007 §7）で「別の URL に変えるとカードが差し替わる」を見る

## 影響

- migration なし（列も表も増えない）。この PR は `docs/adr/**` を含むので auto-merge しない。実装 PR は `drizzle/` を含まないので CI green なら auto-merge してよい
- 実装は 2 PR: **① API**（`PUT` + `getMeal` + タグ張り替え + §5-6 のプレビュー + unit）、**② UI**（`MealFields` の共有化・インライン編集・写真の足し引き・e2e）
- ADR-003 §5「編集 API は持たない。修正は削除 → 再投稿」を撤回。ADR-005 の「複製 + 新規投稿」は別の機能（前回を写して**新しく**記録する）として残る
- ADR-007 §5 の「再取得の導線は持たない」を §5 の形に更新、ADR-004 §6 が送った「投稿後の写真追加 UI」を回収
- requirements 11 に「誰が直せるか / 何が動かないか」を追記（このコミット）、roadmap から本 ADR にリンク（同）

## 却下した選択肢

- **PATCH の部分更新** — §1。2 種類の不在を持ち込む。フォームが全項目を持つ以上、得るものが無い
- **投稿者だけが直せる / 投稿者 + オーナー** — §2。削除がメンバー全員なのに編集だけ絞ると「消せるが直せない」ねじれが残り、認可パターンも 1 つ増える
- **編集履歴（版）を持つ** — 家族数人の食事記録に監査の要件が無い。表が 1 つ増え、CASCADE の子も増える
- **同じ URL の「取り直す」ボタン** — §5。スナップショットの意味を薄めるうえ、外部への出口を表示側に戻す
- **専用ページ / モーダル** — §7。一覧の位置を失う（ページ）、スマホで入力欄とキーボードに窮屈（モーダル）
- **写真を編集の body に含める（多重 multipart）** — 子リソース API が既にあり meal も既にある。1 リクエストに畳む理由が無い
