# ADR-012: 「作った人」（記録した人とは別の、複数人えらべる作り手）で確定した決定

- ステータス: 承認
- 日付: 2026-09-07

## コンテキスト

requirements.md 機能要件 17「作った人」を実装する。

いま記録に載っている人は `meals.created_by`（記録した人）だけで、一覧・詳細の下に「◯◯ が記録」と出る。だが家族のスペースでは**作った人と記録した人が食い違う**のが普通で（作った人がその場で写真を撮って記録することもあれば、食べた側が「おいしかった」と記録することもある）、あとから壁を眺めて「これ誰が作ったんだっけ」が分からない。二人で作った回もある。

決めるのは 6 つ — ①どこに持つか、②作った人がスペースを抜けたらどうなるか、③「メンバーだけ」をどこで守るか、④編集でどう書き換えるか、⑤サジェストで引き継ぐか、⑥フォームでどう選ばせるか。今回の範囲は**記録・表示・編集まで**で、「作った人で絞り込む・集計する」は別 PR（→ 影響）。

## 決定

### 1. `meal_cooks (meal_id, user_id)` の結合表に持つ。`created_by` は動かさない

1 記録に複数人なので `meals` の列にはならない。`meal_tags` と同じ「結合行だけの表」（PK は 2 列、`created_at` も持たない — 行そのものに固有の情報が無い）で、`meals` の CASCADE 子。記録を消せば一緒に消える。

`created_by`（記録した人）は**そのまま残す**。読み替えない — 「誰が記録したか」は監査の情報（[ADR-008](008-meal-edit.md) §2 のとおり認可軸ではない）で、「誰が作ったか」は思い出の情報。同じ列に 2 つの意味を持たせると、片方を直したときにもう片方が壊れる。

表示は 1 行に畳む（`formatCredit`）: 作った人が先で、記録した人は後ろ。0 人なら今までどおり「◯◯ が記録」だけ、作った人と記録した人が同じ 1 人なら「◯◯ が作って記録」と 1 度だけ言う（同姓同名を取り違えないよう、比べるのは表示名ではなく user id）。

### 2. 行は「過去の事実」。スペースを抜けても消さない

名前は `space_members` ではなく `users` から引く（join しない）。スペースを抜けた家族が作った記録も「◯◯ が作った」のまま残る — 作ったという事実は、いま同じスペースにいるかどうかで変わらない。`user_id` の FK は `meals.created_by` と同じく CASCADE にしない（user を消しても記録を道連れにしない）。

### 3. 「メンバーだけが作った人になれる」は SQL が守る

型では表せない（実在するメンバーかどうかは DB にしか無い）ので、境界で守る: `INSERT INTO meal_cooks … SELECT ?, user_id FROM space_members WHERE space_id = ? AND user_id = ?`。他人の user id を送っても SELECT が 0 行なので行は増えない — タグ id の解決（[ADR-003](003-meals-tags.md)）と同じ手で、事前に読んで確かめる往復も、その間に抜けられる隙間も無い。

zod は形（uuid・20 人まで・重複を畳む）だけを見る。**応答の `cooks` は入力の写しではなく書けた行を読み直したもの**なので、落ちた id はクライアントにもそのまま伝わる。

### 4. 編集は「張り替え」ではなく足し引き

`meal_tags` は全部消して入れ直す（[ADR-008](008-meal-edit.md) §3）が、作った人は同じにできない: §3 の INSERT はメンバーしか通さないので、全部消すと**抜けた人の「作った」が、誰かの無関係な編集（打ち間違いの修正）で黙って消える**。そこで、外れた人だけ消し（`DELETE … WHERE meal_id = ? AND user_id NOT IN (…)`）、残った人には触らない（INSERT は `ON CONFLICT DO NOTHING`）。読み直しの往復は要らず、SQL 2 種で差分になる。

編集フォームの札は「いまのメンバー **+ その記録で作った人**」。抜けた人は選ばれた札として見え、残すのも外すのも選べる（見えないまま消えるのが一番悪い）。

### 5. サジェストでは引き継がない

サジェストが複製するのは料理の属性（リンク 2 種・作り方メモ・タグ — [ADR-005](005-meal-suggestions.md) §5 / [ADR-007](007-recipe-links-ogp.md) §1）。作った人は**その回のもの**で、同じ料理でも作る人は回ごとに変わる。日付・タイミング・ひとことメモと同じ扱いにする。

### 6. 札を押して選ぶ。既定はどれも押されていない

タグの絞り込みと同じ押下状態のボタン（`aria-pressed`）を、スペースのメンバーぶん並べる。並びは**自分が先頭、残りは表示名の順**（作ったのが自分の回が一番多い。表示名の比較はサーバーが `cooks` を返す並びと同じ素の文字列比較 = SQLite の BINARY 照合）。

**自分を既定で選んでおかない。** 1 タップは減るが、外食の記録や家族が作った回で外し忘れたぶんが「自分が作った」として残る。この機能は「誰が作ったか分かる」ためにあるので、黙って入る誤りは 1 タップより高くつく。空 = 「作った人は記録していない」で、外食にはその意味がちょうど合う。

## 影響

- migration `0007_meal_cooks.sql` は **`CREATE TABLE` だけの完全 additive**（既存表に触らない = D1 の rebuild と CASCADE 事故が無い — skill `cloudflare-d1-drizzle-migration`）
- API の形が増える: `Meal.cooks: {userId, displayName}[]`（GET / POST / PUT の応答）と `MealContentBody.cookUserIds: string[]`（POST / PUT の入力）。互換層は無い（家族しか使っていない）
- unit 200（+13。`cookOptionsFor` / `mergeCookOptions` / `toggleCook` / `formatCredit` と `cookUserIds` の zod・フォームの往復）
- e2e（golden path）に作った人の段を足した: 記録するときに札を押す → カードと詳細に「e2e-owner が作って記録」→ リロードで残る → 編集フォームで札が押されたまま → 直さずに保存しても消えない（§4 の足し引き）
- 据え置き（別 PR）: **作った人で絞り込む**（ホームの `?cook=`）と**ふりかえりの「誰が何回作ったか」**。`meal_cooks` に `user_id` からの索引が要るのはそのときで、`CREATE INDEX` は additive なので今は足さない

## 却下した選択肢

- **`meals.cook_user_id` の 1 列** — 二人で作った回が書けない（要件は複数選択）。列の追加は additive でも、あとで複数化すると表を割り直すことになる（[ADR-010](010-multiple-links.md) で URL に起きたのと同じ）
- **`created_by` を「作った人」として読み替える** — §1。記録した人と作った人は別物で、片方しか持てなくなる
- **アカウントの無い人も自由入力で書ける（「おばあちゃん」）** — 要件は「スペースに参加してる人から選ぶ」。文字列にすると表記ゆれの名寄せが要り、次の一手（絞り込み・集計）で使えない。必要になったら別 ADR
- **既定で自分を選んでおく** — §6。外し忘れが誤った記録として残る
- **`meal_tags` と同じ張り替え（全部消して入れ直す）** — §4。抜けた人の行が戻せない
- **選んだ順を `position` で持つ** — 人の並びに意味は無い（レシピ URL の順とは違う）。表示は名前順で足りる
- **「外食」「お店」を札の選択肢に入れる** — 0 人がその意味をすでに持っている。人でないものを人の一覧に混ぜない
